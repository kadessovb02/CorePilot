# Workflow benchmarks

The comparative harness supports a single agent loop, planner → coder → reviewer, and the bounded controlled workflow. All arms use the **same model and server**. A comparison of two arms alternates AB/BA order; reversal of three arms is not a fully balanced three-arm design. This measures workflow behavior, not a fleet of separately trained specialists or parity with commercial agents.

The public [synthetic_v1 suite](../benchmarks/synthetic_v1/) contains 12 code changes and 8 read-only inspections of a small inventory package. Each run starts from a fresh copy. The agent can see the repository, its contracts and its style instructions. Case definitions, reference mutations, reference answers and grading code remain outside its workspace until generation finishes. Training and retrieval memory are disabled.

Version 1 was initially held out, but its traces have now informed harness and prompting fixes. Subsequent v1 runs are development and regression evidence, not a fresh held-out estimate. A fresh synthetic v2 suite was frozen before inference. Its first comparison stopped after **2/40 graded attempts**, with 38 never started; that partial record is published below, not as a full-suite quality estimate. Keep its reference solutions and grading criteria separate from harness tuning.

## Scoring

An edit passes independent behavior, API compatibility, existing-behavior and source integrity checks. The grader permits the requested source change and new test files; it rejects unrelated source changes. Agent-written tests and the reviewer's approval do not decide the score.

Read-only cases additionally require observed successful reads, unchanged files, verified source facts and bounded answer criteria. These text criteria are proxies: a passing score does not establish complete factual accuracy, and a valid paraphrase can fail them. Raw answers and tool histories stay in local state for manual review.

The published **usable pass** requires a completed agent task and a passing external oracle. We also report oracle passes separately, since a cancelled or incomplete task can leave a correct patch. Failures, timeouts and resource cancellations count as failed attempts. Unattempted runs are reported separately and never counted as failures or omitted silently.

Speed comparisons use only paired tasks that both workflows pass. Median time across all attempts is an operational diagnostic: a fast failure is not a speed improvement. Paired wins and ties describe this sample; one trial on a small synthetic suite is insufficient for confidence intervals or broad quality claims.

## Resource limits

The runner makes one request at a time, waits three seconds between completed model requests, and rests twenty seconds between tasks by default. Request pacing is configurable with `--request-pause-seconds`; lowering it does not disable resource admission or monitoring. Admission is checked before each run, with a resource watcher during execution. Its default limits are:

- Normal OS memory pressure and at least 2 GiB of estimated reclaimable memory.
- At most 6 GiB combined RSS or macOS physical footprint for explicitly monitored processes.
- No more than 512 MiB growth in system swap from the baseline.
- Stop on an observed thermal warning or CPU performance limit below 100%.

`--allow-memory-warning` is an explicit opt-in that permits known warning-level memory pressure (level 2). The default remains normal pressure. Critical or unknown pressure still blocks admission or stops execution; the configured available-memory reserve, RSS/footprint caps, swap-growth limit and thermal guards remain active. `--min-available-gib` sets the reserve to a finite, nonnegative value and defaults to 2.0. An explicit setting such as `--min-available-gib 1.5` changes admission, not the model's measured memory requirement. Reports record both `resource_thresholds.allow_memory_warning` and `resource_thresholds.min_available_gib`, including when admission blocks every attempt.

`--max-swap-growth-mib` sets the maximum measured system-wide swap growth from the experiment baseline; it accepts a finite, nonnegative value and defaults to **512 MiB**. An explicit larger limit permits more swap growth before cancellation, without changing the other guards. Reports record `resource_thresholds.max_swap_growth_mib`. Sampling can observe an overshoot between checks; the configured limit is not a guarantee of an exact peak.

Required memory counters being unavailable blocks admission. macOS footprint includes allocations that simple RSS may miss; observations are sampled and can miss short peaks. Available memory is an estimate, and swap/pressure reflect all applications. `pmset` often provides no thermal reading: null values mean **unknown**, not zero temperature or proof that the laptop stayed cool.

The monitor cancels the task and stops further calls on a limit or timeout. Client cancellation cannot guarantee an external server has stopped generating. The person running the experiment must confirm it is idle or stop an owned benchmark server before restarting. The harness never kills other applications or changes OS settings.

Wall time includes model calls, tools, orchestration and the configured request pauses. It excludes the external grader and the pause between tasks. `inference_seconds` records client-observed HTTP completion time, including server queuing; it is not pure GPU time. HTTP attempts and server-reported prompt/completion/cache token counts are reported separately from logical agent calls. Missing usage is not estimated. The same character context limit is used in both modes; this does not imply identical token counts because role instructions differ.

The configured character cap applies to conversation compaction; JSON action instructions and tool schemas are appended afterwards. It is not a hard cap on the final HTTP payload. Server-reported token usage describes the actual requests.

At task creation, root `AGENTS.md` and `CLAUDE.md` are included as untrusted repository guidance, with at most 3,000 characters from each safe, readable file. Unsafe paths, symlinks, files over the file-size limit and unreadable text are skipped. Guidance and retained evidence precede the objective; later user corrections remain task requests. Compaction reserves bounded space for guidance before recent conversation groups, retains whole excerpts when they fit, and clearly marks further shortening. These excerpts are not a complete or continuously refreshed copy of repository instructions: the agent must read a named file for its full, current contents. Automatic inclusion does not count as an observed tool read for the inspection oracle.

When a server reports `finish_reason: "length"`, the partial response cannot complete a task or specialist phase. Valid parsed tool calls still receive recorded, paired results. The engine permits at most two continuations within the existing call/time budgets, without increasing the token cap. Further truncation interrupts the task and preserves its checkpoint. A server that omits this finish reason cannot receive the same truncation detection from CorePilot; task completion and the external oracle remain separate measurements.

For free-form and specialist tasks, the current engine renders a fresh budget paragraph in the first SYSTEM message for every model request. It shows the charged global/role call number and requests remaining **after that response**, using the actual task and phase limits. It is a transient copy, so counters do not accumulate in checkpoint messages or displace the objective and later corrections. A planner receives a soft target of at most six calls or roughly one third of the global allowance at phase start, bounded by the role cap, with the remainder reserved for coding and independent review as applicable. Its instructions scope exploration to unresolved questions, reuse successful observations of unchanged files, and request a concise handoff once observations support the contract. The hint never forces a phase transition or relaxes actual-read, source-integrity or current-check requirements. Recorded command success and model approval remain separate from external behavioral correctness.

The same transient SYSTEM paragraph lists the planner's required unread root `AGENTS.md`/`CLAUDE.md` files. Only successful `read_file` results in that phase satisfy the status; automatic excerpts, failed reads and another role's or earlier phase's observations do not count. A planner is instructed to finish with concise assistant text and no tool calls when ready; that response hands work to the next specialist, without completing the user's task. For read-only tasks, the reviewer's published summary is instructed to contain the requested explanation grounded in observed files and relevant references. These instructions do not independently guarantee answer quality.

The current loop guard watches consecutive successful `read_file`, `list_files` and `search` results. It compares the tool name, canonical arguments and full actual result. After at least three identical observations, it records one verification event and includes bounded coaching in the next model request's SYSTEM message. Only a returned model response marks that opportunity as received. If the following tool batch continues the same unchanged streak, the task is interrupted and its actual checkpoint is retained. Complete batches receive all paired replies before coaching or interruption, and a different operation or argument/result, a failure, phase change or resume resets the streak. Commands are not counted as repeated reads. It neither approves work nor advances a phase; actual-read and check gates remain active. Alternating or argument-varied loops are outside this exact-identical detector and remain subject to task call/time caps.

## Reproduce

Install the repository and run the CPU-only fixture audit first:

```sh
python -m pip install -e '.[dev]'
python benchmarks/synthetic_v1/selfcheck.py
python -m pytest -q tests/test_benchmark.py tests/test_benchmark_resources.py
```

Start one suitable model server separately. Keep runtime state, downloaded models and raw task traces outside this checkout. Use the same fixed weights and server configuration for both workflows, with no private adapter. A small reproducible candidate is [Qwen2.5-Coder-1.5B-Instruct, MLX 4-bit](https://huggingface.co/mlx-community/Qwen2.5-Coder-1.5B-Instruct-4bit), derived from [Qwen's official model](https://huggingface.co/Qwen/Qwen2.5-Coder-1.5B-Instruct). Pin its revision and record your actual server versions and launch settings. Suitability must be measured on the target machine.

```sh
python scripts/run_benchmark.py \
  --state "$TMPDIR/corepilot-benchmark-fresh" \
  --output "$TMPDIR/corepilot-comparison.json" \
  --url http://127.0.0.1:8108/v1 --model default_model --protocol json \
  --server-pid YOUR_SERVER_PID \
  --rest-seconds 20 --request-pause-seconds 3 --timeout 150 --max-calls 24 \
  --max-tokens 768 --context-chars 14000
```

Choose a new state directory for each experiment. `--limit N` selects the first N cases for a declared pilot; do not select cases after observing model outcomes. `--metadata` accepts a reviewed JSON object with public model identity, revision, hardware, package versions and code fingerprints. Do not put credentials or machine paths there.

Choose `--protocol json` (the default) for JSON actions or `--protocol native` for native tool calls. The selected protocol is explicit, applies to both workflows and has no automatic fallback. The initial full and partial trials used JSON actions; later development pilots select native or JSON explicitly as recorded below. Temperature is 0.15, with no history/retrieval and one stochastic trial per mode. By default, per-case call/time limits are defined in the suite and capped by CLI budgets. Optional `--case-call-override` (default **None**, integer 1–100) replaces each suite case's call cap, still bounded by `--max-calls`. It applies the same total task cap to both workflows, not a separate allowance per specialist. `--case-timeout-override` likewise replaces suite time caps while `--timeout` remains an upper bound. Both overrides are explicit and recorded in report settings; declaring them changes the experiment rather than editing the frozen suite. Cache contents are not reset; AB/BA order alternates by case. A sixteen-token warm-up, if performed, must be disclosed and excluded from scored tasks. A short health warm-up does not verify that a model can follow the longer tool protocol.

```sh

  --suite benchmarks/synthetic_v3 --state "$TMPDIR/corepilot-v3-fresh" \
  --output "$TMPDIR/corepilot-v3-report.json" \
  --url http://127.0.0.1:8108/v1 --model default_model --protocol native \
  --mode controlled --mode single \
  --case-id edit-tag-normalization --case-id inspect-tag-current \
  --check-json '["python","-m","unittest","discover","-s","tests","-v"]' \
  --server-pid YOUR_SERVER_PID --max-calls 8 --max-tokens 2048 \
  --context-chars 22000 --timeout 180 --rest-seconds 60
```

The source suite remains unchanged when selecting a subset. The report records selected IDs, modes and the full suite fingerprint. Both modes grade partial work after a deadline but never count it as usable; a deadline stops further attempts. Resource-aborted work is ungraded. Generation resource sampling ends and its watcher drains before CPU grading, preventing a late stop from being recorded as a successful task.
